# 成果物文書アーキテクチャの設計思想

このドキュメントは「なぜ成果物文書をこの形で体系化しているか」という原則をまとめたものです。
個別の実装決定記録（いつ・何を・どう変えたかの作業ログ）は本書の対象外です。
本書は今後 Skill を追加・改修するたびに立ち返る「原則」を扱います。

## 背景: コンテキストは成果物文書である

Skill（実行プロセス）と同じくらい重要なのが、開発の過程で生成されるコンテキスト情報である。
プロジェクト開発におけるコンテキストとは、要件定義書・設計仕様書・テスト戦略書のような
**開発の成果物であるドキュメントそのもの**を指す。プロセス（段階・ゲート）をどれだけ整備しても、
そこから生まれる文書の構造がばらばらであれば、後から読む人・AI は必要な情報を探すコストを
毎回払うことになる。したがって改善の焦点は「実行手順」だけでなく「ドキュメントの体系化」にも
向ける必要がある。

## 原則1: 「生成AIが効率的に利用可能」とは探索コストがないこと

目指す状態は、後続の別セッション・別Skillがドキュメントを読んだ時に、必要な情報を
**迷わず正確に拾える**ことである。これは機械可読性（YAML frontmatterや厳密なキー命名）を
最優先することとは異なる。人間の可読性を保ったまま、見出し・項目名・順序を全文書種別で統一し、
「決定事項はどこか」「未決事項はどこか」を毎回同じ場所で探せるようにする方が実利が大きい。

## 原則2: 共通スケルトン + 種別固有の詳細章

成果物文書は種別ごとに専門的な内容（ERD、比較した代替案、受入条件 等）を持つが、
文書情報・目的背景・対応元ID・方針決定事項・制約・未決事項・関連リンク・変更履歴といった
「探すときに必ず見る場所」は全種別で共通化する。個別最適な文書をゼロから設計するのではなく、
共通の骨格に種別固有の詳細章を差し込む2層構造にすることで、体系の一貫性と個別文書の専門性を
両立させる。

## 原則3: トレーサビリティは逆リンクのみ、中心集約マトリクスは作らない

各文書は自身の「文書ID」（例: `REQ-001`）を持ち、下流の文書は「対応元ID」セクションで
上流の文書IDを逆参照する。要件→設計→テストのような連鎖は、この逆リンクを辿ることで
後から追跡できる。中心に一つのトレーサビリティマトリクス文書を置いて全対応関係を管理する
方式は、精度は上がるが毎回の更新が運用負荷になり形骸化しやすいため、あえて採用しない。
運用が続けられる最小限の仕組みを優先する。

## 原則4: 実行ログと成果物文書は別物として扱う

`assets/*-log-template.md`（Skill実行の記録・振り返り用、append-only）と、
`shared-templates/document-templates/`（対象プロジェクトに配置される成果物文書そのもの）は、
役割が異なるため統合しない。前者は「このSkill実行で何をしたか」の証跡、後者は
「次工程やAIが読むコンテキスト」である。この境界を崩すと、証跡としての追記専用性と、
成果物としての最新性という相反する要求が同じファイルに同居してしまう。

## 原則5: プロセス構造とドキュメント構造は独立して変更する

Skillの段階番号・ゲート・mermaid図（プロセス構造）と、成果物文書の章立て（ドキュメント構造）は
別々の関心事として扱う。ドキュメント構造の改善のために段階番号を振り直す、あるいはその逆を
行うと、変更の影響範囲が本来の目的を超えて肥大化する。過去に段階リナンバリングを伴う設計案を
一度採用しかけて破棄した経緯があり、この分離は実際の失敗から得た教訓である。

## この原則の使い方

新しい Skill を追加する、または既存 Skill の成果物文書を見直すときは、以下を確認する。

- [ ] 対応する成果物文書テンプレートが [document-templates/README.md](../shared-templates/document-templates/README.md) の索引にあるか。なければ共通スケルトンに沿って新設する
- [ ] 文書IDのプレフィックスが [traceability-id-convention.md](./traceability-id-convention.md) と重複しないか
- [ ] 対応元IDセクションで、上流文書への逆リンクが説明できる状態になっているか
- [ ] プロセス構造（段階・ゲート）を変更していないか。変更が必要な場合は本書の原則5に照らして別タスクとして切り出す
